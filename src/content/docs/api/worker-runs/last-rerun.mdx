**Method:** `POST`

**Endpoint:** `/api/v2/worker-runs/last/rerun`

**Authentication:** Supports `Authorization: Bearer <YOUR_API_KEY>`, `api-key: <YOUR_API_KEY>`, and `?token=<YOUR_API_KEY>`. Prefer Bearer token.

## Try it

<ApiPlayground method="POST" path="/api/v2/worker-runs/last/rerun" />

## When to use this endpoint

Use this endpoint to create a new run from an existing run. The response returns a new `run_slug`.


## Request Body

Send the request body with `Content-Type: application/json`. Required/Optional describes each field; the Try it Request Body badge shows whether the body itself is required.

| Field | Required | Type | Description |
| --- | --- | --- | --- |
| `callback_url` | No | `string` | Callback URL. When provided, CoreClaw sends a `POST` request after the run status changes or finishes. |
| `is_async` | No | `boolean` | `true` submits asynchronously without waiting for results; `false` waits for the run to finish. Defaults to `true`. **Sync mode waits at most 5 minutes; if the run has not finished by then, the request returns and you must poll status via the run query endpoint.** |
| `limit` | No | `integer` | Synchronous result window size for runs or reruns. It only controls how many result rows are included in the synchronous response, not the full result set. Constraints: default `20`; range 1-100. |
| `offset` | No | `integer` | Page number for the synchronous result window, 1-based. `offset=1` is page 1; `offset=0` is accepted as page 1. Only affects the result window in the sync response, not the full result set. Constraints: default `0`; minimum 0. |

### JSON Example

```json
{
  "callback_url": "https://client.example.com/openapi/callback",
  "is_async": true,
  "limit": 20,
  "offset": 0
}
```

## Run Mode

- `is_async: true` submits the run asynchronously and returns without waiting for execution results. The response includes `data.run_slug`; then poll the run detail, log, and result endpoints.
- `is_async: false` waits for the run to finish, equivalent to run-and-wait behavior. Use `offset` / `limit` to control the result window returned by the synchronous run.

> **⚠️ Sync wait limit: 5 minutes.** When `is_async: false`, the platform waits for the run for **up to 5 minutes at most**. If the run has not finished within 5 minutes, the request returns anyway and the run keeps executing in the background — you must then use the run **query endpoint** to poll status, logs, and results by `runId`. For runs that may exceed 5 minutes, prefer `is_async: true`.

## Request Example

```bash
curl -X POST "https://openapi.coreclaw.com/api/v2/worker-runs/last/rerun" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  --data '{"callback_url":"https://client.example.com/openapi/callback","is_async":true,"limit":20,"offset":0}'
```

## Response Example (Async)

When `is_async: true` (default), the response returns the new `run_slug` immediately:

```json
{
  "code": 0,
  "data": {
    "run_slug": "01KKDXV2G26BT7NH4ZQR2R4NPZ"
  },
  "message": "success",
  "request_id": "req-123"
}
```

## Response Example (Sync)

When `is_async: false`, the response waits for the rerun to finish and returns the run status, timing, and a paginated result window. The `results` object uses the same shape as `GET /api/v2/worker-runs/{runId}/result`. Rerun sync responses include `is_finished` and omit `error_message`/`result_message`:

```json
{
  "code": 0,
  "data": {
    "run_slug": "01KZAZV240082MSQD1K5J6R3NF",
    "run_status": "succeeded",
    "execution_start_timestamp": 1786001100,
    "execution_end_timestamp": 1786001107,
    "running_duration": 7,
    "is_finished": true,
    "results": {
      "count": 1,
      "headers": [
        { "key": "title", "label": "Title" }
      ],
      "list": [
        { "title": "Example result" }
      ],
      "page_index": 1,
      "page_size": 20
    }
  },
  "message": "success",
  "request_id": "req-123"
}
```

### Sync Response Fields

| Field | Type | Description |
| --- | --- | --- |
| `data.run_slug` | `string` | New run identifier. Use it to read detail, log, result, and export. |
| `data.run_status` | `string` | Run status, for example `succeeded` or `failed`. See [Run Lifecycle & Status](/api/run-lifecycle/). |
| `data.execution_start_timestamp` | `integer` | Execution start time, Unix seconds. |
| `data.execution_end_timestamp` | `integer` | Execution end time, Unix seconds. |
| `data.running_duration` | `integer` | Running duration in seconds. |
| `data.is_finished` | `boolean` | Whether the run reached a finished state when the sync wait returned. |
| `data.results` | `object` | Paginated result window. Same shape as the result endpoint: `count`, `headers`, `list`, `page_index`, `page_size`. See [List Worker Run Results](/api/worker-runs/result/). |

> `run_status` is authoritative. If `is_finished` is `false` or the sync wait timed out, poll the run detail endpoint for the final status.

## Notes

- API v2 supports Bearer token, the legacy `api-key` header, and query token. Prefer Bearer token for new integrations.
- This is an account-level latest-run endpoint and does not take a `workerId` path parameter; it operates on the latest run in the current account scope.
- `last` means the latest run in the current scope. Use a concrete `runId` endpoint when the target must be explicit.
- See [Run Lifecycle & Status](/api/run-lifecycle/) for status handling, polling, failure diagnosis, and cancellation behavior.
- When `callback_url` is provided, CoreClaw sends callback notifications after status changes or completion. See [Callback Notifications](/api/callbacks/).
